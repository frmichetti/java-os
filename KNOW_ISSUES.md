# Known Issues

## ~~Rótulos de dados sem prefixo em `global_asm!` colidem entre diferentes programas de teste de modo usuário~~ (RESOLVIDO)

**Status:** descoberto durante a implementação da change `kernel-fpu-context-switch` (ver `openspec/changes/kernel-fpu-context-switch/design.md`), ao rodar `cargo test -p kernel --lib` depois de uma mudança em `kernel/src/lib.rs` (adição de `pub mod fpu;`) invalidar o cache incremental e forçar uma recompilação completa. **Corrigido** na mesma sessão (tarefa de pré-requisito antes do restante da change poder ser verificada).

**Sintoma observado:** `cargo test -p kernel --lib` falhava com vários erros `error: symbol 'X' is already defined` (ex.: `msg`, `msglen`, `msg_end`, `st0`..`st7`), apontando para dentro de blocos `global_asm!` de módulos de demonstração diferentes (`kernel::file_syscalls_demo`, `kernel::user_posix_demo`, `kernel::user_demo`). `cargo kernel-build`/`cargo xtask run`/`cargo xtask test` nunca mostraram esse erro — só `cargo test --lib`, e só depois de uma recompilação completa (não incremental).

**Causa raiz:** vários módulos de demonstração em modo usuário (cada um com seu próprio `global_asm!` independente) usam os mesmos nomes de rótulo internos (de dados: `msg`, `msglen`, `msg_end`, `st0`..`st7`/`st11`) para o mesmo propósito (mensagem de resultado, marcadores de `'P'`/`'F'` por cenário) — convenção copiada de um módulo para o próximo sem perceber que esses rótulos, sem nenhum prefixo, são símbolos **globais** de verdade no assembler, não escopados ao módulo Rust que os declara. Quando o compilador mescla o conteúdo de múltiplos `global_asm!` do crate inteiro na mesma unidade de montagem (o que não acontecia de forma confiável sob compilação incremental, mascarando o problema), rótulos com o mesmo nome definidos em arquivos diferentes colidem.

**Correção aplicada:** todos os rótulos internos (não as funções de entrada/saída como `_start`/`_end`, que precisam permanecer globais e já tinham nomes únicos por arquivo) passaram a usar o prefixo `.L` (rótulo local de verdade — nunca aparece na tabela de símbolos do linker) **mais um prefixo curto único por arquivo** (`.Lfsd_` em `file_syscalls_demo.rs`, `.Lupd_` em `user_posix_demo.rs`, `.Lud_` em `user_demo.rs`, `.Led_` em `exit_demo.rs`). **Achado durante a própria correção:** só o prefixo `.L` sozinho não basta — ele esconde o rótulo do linker, mas o assembler ainda exige que o nome seja único dentro da mesma unidade de montagem (ao contrário dos rótulos puramente numéricos como `1:`/`2:`, que são de fato reutilizáveis livremente via a sintaxe `1f`/`1b` — por isso esses nunca colidiram). Só rótulos numéricos continuam sem prefixo.

**Nota metodológica para investigações futuras:** ao adicionar um novo módulo de demonstração em modo usuário com `global_asm!`, qualquer rótulo de dados nomeado (não numérico) deve usar `.L<prefixo_do_arquivo>_<nome>` desde o início, nunca um nome "óbvio" como `msg`/`buf`/`st0` sem prefixo — o bug fica dormente sob compilação incremental e só aparece numa recompilação completa, o que pode acontecer muito depois do módulo problemático ter sido escrito.

## ~~Duas threads de kernel imprimindo concorrentemente travam o timer de hardware para sempre~~ (RESOLVIDO)

**Status:** descoberto durante a implementação da change `kernel-wait-queue` (ver `openspec/changes/archive/2026-11-03-kernel-wait-queue/design.md`, seção "Achados durante a implementação" — nº 2), ao tentar ligar `kernel::wait_demo` (produtora/consumidora) em boot real. **Corrigido** em manutenção posterior (fora de qualquer change formal, a pedido direto do usuário) — ver "Causa raiz" e "Correção" abaixo.

**Sintoma observado:** assim que uma segunda thread de kernel (além de `kernel::user_demo`, que já imprime em laço apertado via *syscall*) chama `serial_println!` repetidamente, o kernel travava por completo após 1-4 impressões dessa segunda thread — nenhuma mensagem nova aparecia no console serial depois disso, nem mesmo as de `user_demo` (que até então imprimia continuamente).

**Causa raiz (confirmada via GDB, anexado ao QEMU travado):** `kernel::serial::_print` (usada por `serial_println!`/`serial_print!`) fazia `SERIAL1.lock()` e, separadamente, `crate::framebuffer::mirror(args)` (que faz `CONSOLE.lock()`) **com interrupções habilitadas** durante toda a formatação/desenho dos glifos. Uma thread comum podia ser legitimamente preemptada pelo timer no meio dessa seção crítica, com o lock de `CONSOLE` retido. A *syscall* de escrita (`kernel::syscall::sys_write`, que também usa `CONSOLE`/`SERIAL1`) roda com interrupções **desabilitadas** (`IA32_FMASK` mascara `IF` durante toda a `syscall`, ver `kernel::syscall::init`) — então, se `sys_write` precisasse do mesmo lock de `CONSOLE` enquanto outra thread o detinha, seu `Spinlock::lock()` girava em busy-wait **com `IF` já em zero**: a própria espera impedia a entrega da próxima interrupção do timer, que é exatamente o que devolveria a CPU à thread que detinha o lock para ela terminar e liberá-lo. Impasse clássico de "lock retido com interrupções habilitadas, disputado por código que já roda com interrupções desabilitadas" — o kernel já tinha essa mesma categoria de cuidado documentada e aplicada para `kernel::scheduler::READY_QUEUE`/`CONTEXTS` (`with_interrupts_disabled`) e para `kernel::wait_queue`, mas nunca para os locks de impressão (`SERIAL1`/`CONSOLE`), já que nenhuma change anterior jamais teve duas threads imprimindo continuamente ao mesmo tempo para expor o problema.

**Correção aplicada:** `kernel::serial::_print` e `kernel::serial::MirroredWriter::write_str` agora envolvem toda a seção crítica (`SERIAL1.lock()` + `crate::framebuffer::mirror`/`mirror_str`) em `kernel::scheduler::with_interrupts_disabled`, tornando cada impressão atômica em relação a interrupções — nenhuma chamada pode mais ser preemptada com um desses locks retido. `kernel::syscall::sys_write` não precisou de mudança (já roda inteiramente com `IF=0` via `SFMASK`).

**Nota metodológica para investigações futuras:** uma parte da investigação original foi confundida por um artefato de teste — rodar `timeout <N>s qemu-system-x86_64 ...` mata o processo exatamente aos N segundos, podendo cortar uma escrita no meio e deixar a última linha do log serial truncada **mesmo quando o kernel não travou de verdade**. Uma linha cortada ao final de um log não é, por si só, evidência de travamento: a verificação confiável é amostrar `kernel::timer::TICKS` duas vezes (poucos segundos de intervalo) via GDB anexado (`qemu-system-x86_64 ... -s`, sem `-S`, depois `gdb -q -batch -x cmds.txt target/x86_64-java_os/debug/kernel` com `target remote localhost:1234`) e confirmar que o valor realmente parou de incrementar, ou contar quantas mensagens completas se acumularam ao longo de uma janela maior em vez de olhar só a última linha.

## ~~IRQ1 (teclado) entregue só uma vez por sessão de boot a 100 Hz sob QEMU/TCG~~ (NÃO É UM BUG DO KERNEL)

**Status:** investigado a fundo na change `kernel-keyboard` (ver `openspec/changes/archive/.../design.md`, seção "Achados durante a implementação") — confirmado como limitação de timing da emulação por software do QEMU (TCG), não um defeito do kernel. Nenhuma correção de código necessária.

**Sintoma observado:** com o escalonador na frequência padrão de 100 Hz, uma tecla simulada via `sendkey`/QMP no QEMU era recebida e traduzida corretamente, mas nenhuma tecla seguinte (mesmo minutos depois, em conexões separadas) disparava uma nova interrupção. `info lapic` do monitor do QEMU mostrava o vetor do teclado permanentemente pendente em IRR, nunca promovido a ISR.

**Diagnóstico:** descartados como causa (todos testados e refutados com evidência real via GDB/`info lapic`): entrada do I/O APIC mascarada/presa, prioridade do vetor da IDT, IMCR, polaridade/modo de disparo, número de espaços de endereçamento em rotação a cada tick. O fator decisivo foi a frequência do timer: a 2 Hz e 20 Hz a entrega era perfeitamente confiável; só falhava a 100 Hz. **Confirmação definitiva**: rodando com aceleração de hardware real (`-accel kvm -cpu host`) em vez de TCG, a 100 Hz, toda a sequência de teclas foi entregue perfeitamente — prova que o driver está correto e a falha é específica da emulação por software do QEMU sob alta frequência de interrupção concorrente.

**Implicação prática:** verificação manual de drivers de IRQ externa via `cargo xtask run`/`sendkey` sob QEMU padrão (sem KVM) pode mostrar só a primeira interrupção simulada — isso é esperado, não indica regressão. Para verificar de verdade um driver de IRQ externa em boot manual, usar `-accel kvm` (requer `/dev/kvm` acessível) quando disponível.

## ~~Ausência de guard page na stack principal do kernel~~ (RESOLVIDO)

**Status:** resolvido pela change `kernel-stack-guard-page` (ver `openspec/changes/kernel-stack-guard-page/` — `design.md` para o racional completo).

**Descoberto em:** change `kernel-interrupts-timer`, tarefa 2.3 (verificação de double fault por estouro de stack).

**Contexto original:** o kernel rodava inteiramente sobre a stack que o Limine configura antes de entregar o controle em `kernel_main` — não havia nenhuma stack própria do kernel, nem uma guard page (região de memória deliberadamente não mapeada) logo abaixo dela.

**Sintoma observado:** ao provocar um estouro real de stack (recursão infinita), o kernel não falhava rapidamente como esperado. Em vez disso, a recursão sobrescrevia silenciosamente uma quantidade significativa de memória adjacente (sem causar nenhuma exceção de página) antes de eventualmente alcançar algo que gerava falha. Quando a falha finalmente ocorria e escalava para um double fault, o handler de double fault era corretamente invocado e executava na stack dedicada de IST1 (confirmado via GDB — `RSP` caía exatamente dentro do range de `DOUBLE_FAULT_STACK`), mas a tentativa de formatar e reportar a mensagem de diagnóstico travava indefinidamente (`RIP` ficava parado dentro de `core::fmt::write`), provavelmente devido a alguma estrutura de dados usada pela formatação ter sido corrompida durante o estouro.

**Correção implementada:** `kernel::stack` mapeia uma stack dedicada de 64 KiB numa faixa virtual isolada (`0xffff_a000_0000_0000`), com a página imediatamente abaixo dela deliberadamente não mapeada (guard page), e `kernel_main` troca para essa stack assim que o alocador de frames/paginação estão prontos. Durante a implementação, descobriu-se que o handler de `#PF` também precisava de sua própria stack via IST (mesmo mecanismo do `#DF`) — sem isso, um estouro de stack escalava direto para `#DF` sem o `#PF` nunca ser entregue, já que a CPU não conseguia empilhar o frame de exceção numa stack já invadida pela guard page (ver `design.md` — "Page fault também precisa de stack dedicada (IST)"). Com essa correção, um estouro real de stack agora produz `EXCECAO #PF (page fault)` com o endereço (`CR2`) dentro da guard page, verificado em boot real via QEMU/GDB.

## ~~`SYSCALL_USER_RSP_SCRATCH` é uma variável global única, corrompida quando uma syscall bloqueante troca de contexto para outra thread que também faz syscalls~~ (RESOLVIDO)

**Status:** descoberto durante a implementação da change `kernel-timed-wait` (tarefa 5.3, verificação em boot real de `/bin/timedw.elf`). A causa raiz é um defeito pré-existente em `kernel::syscall` (mecanismo `syscall`/`sysret`, de uma change bem anterior), não um bug introduzido pelo código novo desta change — corrigi-lo estava fora do escopo original da proposta/tasks.md de `kernel-timed-wait`. **Corrigido na mesma sessão**, a pedido explícito do usuário (consultado via pergunta direta: corrigir agora, fora do escopo formal, vs. adiar e registrar), já que sem a correção a verificação em boot real desta própria change (tarefas 5.3/5.4) não podia ser concluída de verdade.

**Sintoma observado:** ao rodar `/bin/timedw.elf` (chama `pthread_cond_timedwait` com prazo de 50 ms, sem ninguém notificar), o kernel inteiro trava com `EXCECAO #PF (page fault)` pouco depois do timeout expirar e a thread ser devolvida à rotação do escalonador. O log de depuração instrumentado mostrou exatamente:
```
DEBUG spawn_from_elf: path=/bin/timedw.elf thread_id=13 (root=0xde1c000)
DEBUG spawn_from_elf: path=/bin/javaosvm.elf thread_id=10 (root=...)
DEBUG take_block_intent: parking id=13
DEBUG wake_expired_deadlines: candidate id=13
DEBUG wake_expired_deadlines: waking id=13
EXCECAO #PF (page fault): endereco=0x90000000e48 codigo_erro=0x4 rip=0x400325 cr3=0xde1c000 rsp=0x90000000e48
```
`cr3=0xde1c000` é exatamente o `address_space_root` da própria thread 13 (`timedw.elf`) — a troca de espaço de endereçamento está correta. Mas `rsp=0x90000000e48` cai dentro de `JAVAOS_VM_TEST_PROGRAM_STACK_VIRT` (`0x0000_0900_0000_0000`, constante de **outra** thread, `javaosvm.elf`/thread 10) — não dentro de `TIMEDWAIT_TEST_PROGRAM_STACK_VIRT` (`0x0000_0c00_0000_0000`, a própria stack de usuário de `timedw.elf`). `rip=0x400325` é um endereço de usuário válido (código real de `timedw.elf`, já de volta ao modo usuário) — ou seja, o `sysretq` de retorno da syscall devolveu `RIP`/`CS`/`CR3` corretos, mas um `RSP` de usuário que pertence a **outro processo completamente diferente**, que falha na primeira instrução que toca a pilha.

**Causa raiz (confirmada por leitura de código após a reprodução em boot real):** `kernel::syscall::SYSCALL_USER_RSP_SCRATCH` (`kernel/src/syscall.rs`, ~linha 530) é um único `static mut u64` **global, não por-thread**, usado por `syscall_entry` (bloco `global_asm!`) para guardar o `RSP` de modo usuário da chamada em andamento (`mov [SYSCALL_USER_RSP_SCRATCH], rsp` na entrada) e restaurá-lo logo antes de `sysretq` na saída. O comentário original que justifica isso como seguro ("`SFMASK` mascara `IF` durante toda a janela em que este valor está emprestado... não há reentrância possível") é verdadeiro **somente** enquanto a própria syscall nunca cede a CPU para uma thread diferente no meio do caminho. Isso deixou de valer a partir do momento em que uma syscall pode **bloquear de verdade** (`kernel::pthread::Mutex::lock`/`CondVar::wait`/`CondVar::wait_timeout`, todas via `WaitQueue::commit_block()` → `int {BLOCK_VECTOR}` → `scheduler::schedule_next`, que troca de contexto para **outra thread arbitrária**): a thread que bloqueia deixa seu `RSP` de usuário "emprestado" em `SYSCALL_USER_RSP_SCRATCH` por um tempo potencialmente longo (vários ticks do timer), e **qualquer outra thread que faça qualquer syscall nesse meio tempo** (mesmo uma trivial, como `SYSCALL_WRITE`) sobrescreve essa mesma variável global com o próprio `RSP` dela antes de devolvê-la corretamente ao final da sua própria syscall — perdendo para sempre o valor original da thread bloqueada. Quando a thread bloqueada finalmente é despertada e sua chamada original (`sys_cond_wait`/`dispatch`/`syscall_entry`) retoma e chega ao `sysretq` de saída, ela lê de volta o valor deixado pela **última** thread que passou por uma syscall nesse intervalo — não o seu próprio.

Esse defeito já existia desde que `kernel::pthread::Mutex`/`CondVar` passaram a bloquear de verdade (`kernel-pthread-sync`), mas nunca tinha sido exposto: os cenários de boot real anteriores com espera bloqueante via syscall (`jpthread.elf`/`user_posix_demo`) aparentemente nunca tiveram uma janela de bloqueio longa o bastante, com outra thread fazendo syscalls concorrentes nesse intervalo exato, para corromper o valor antes do despertar. `timedw.elf` é o primeiro cenário desta natureza com uma janela de bloqueio garantidamente longa (50 ms ≈ 5 ticks a 100 Hz) e sem nenhum notificador — tempo de sobra para `test.elf` (laço apertado de `SYSCALL_WRITE`) e outras threads corromperem a variável.

**Correção aplicada:** `SYSCALL_USER_RSP_SCRATCH` foi removida; em seu lugar, `kernel::process::Context` ganhou um novo campo `syscall_rsp_slot: u64` — endereço de uma célula `u64` por-thread, alocada via `Box::leak` (mesma disciplina de `fpu_state`/`kernel::fpu::new_area`), nunca liberada. Um novo global `kernel::scheduler::CURRENT_SYSCALL_RSP_SLOT` (mesmo padrão de `CURRENT_FPU_AREA`) é atualizado pelo escalonador a cada troca de contexto (`schedule_next`, `register_boot_thread`) para sempre apontar ao slot da thread que está de fato retomando. `kernel::syscall::syscall_entry` (assembly) agora faz uma indireção: lê o endereço do slot em `CURRENT_SYSCALL_RSP_SLOT` e só então lê/escreve o `RSP` de usuário *através dele* — nunca mais diretamente numa única `static`. **Achado real durante a correção:** o primeiro rascunho usava `RAX` como registrador temporário para essa indireção, mas `RAX` carrega o número da syscall na entrada (ainda necessário mais adiante, em `mov rdi, rax`) — corrigido adiantando `mov r8, r10` (já necessário para o 5º parâmetro de `dispatch`) para liberar `R10` como temporário, em vez de `RAX`; `RBX`/`RBP`/`R9`/`R12`-`R15` nunca são tocados por este trecho (preservados implicitamente pela convenção `syscall`, igual já documentado para o restante de `syscall_entry`). Verificado em boot real: `timedwait_test_program: resultado PP (ordem: etimedout,elapsed_ge_requested)`, sem `EXCECAO` nenhuma, e todos os demais programas de teste (`javaos_pthread_test_program`, `libm_test_program`, `javaos_vm_test_program`, etc.) continuaram reportando exatamente os mesmos resultados de antes.

**Nota metodológica para investigações futuras:** o `cr3` correto combinado com um `rsp` de outro processo é a assinatura característica deste bug — qualquer `EXCECAO #PF` futura com essa combinação (`cr3` da própria thread, `rsp`/`CR2` dentro da faixa `*_STACK_VIRT` de **outra** thread) deve ser investigada aqui primeiro, antes de suspeitar do código novo que estava sendo testado no momento.
