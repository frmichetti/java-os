# Design

## Context

Ver `proposal.md` — Why/What Changes. O kernel hoje oferece, nativamente (não-POSIX): `kernel::paging::Mapper::map`/`map_new` (mapeamento explícito de páginas de 4096 bytes com `PageFlags`, sem *demand paging* — toda página mapeada já está resolvida), `kernel::phys::FrameAllocator` (alocação de frames físicos), `kernel::scheduler`/`kernel::process` (processos com espaço de endereçamento próprio, threads com escalonamento preemptivo round-robin, mas sem nenhuma API pública de criação de thread "estilo pthread" fora do kernel), `kernel::sync::Spinlock` (exclusão mútua só por *busy-wait*, sem bloqueio/sono de thread), e um `page_fault_handler` único instalado na IDT (vetor 14) que hoje trata qualquer *page fault* como evento fatal — não há mecanismo de "proteger uma página específica e redirecionar a execução para um handler escolhido pelo chamador" (o que o polling de safepoint do HotSpot exige). Não há `syscall` de E/S de arquivo (as duas chamadas existentes, de `kernel-syscalls`, são escrita no console e consulta de ticks) nem qualquer coisa parecida com um carregador de ELF dinâmico.

Pesquisa feita para este design (buscas na documentação pública do OpenJDK/HotSpot e em código-fonte espelhado, já que não há como compilar/rodar o HotSpot de verdade neste ambiente — ver `Fontes consultadas` ao final):
- A camada `os`/`os_posix`/`os_linux` do HotSpot expõe, para o resto da VM, operações de reserva/commit/descommit de memória virtual (`os::reserve_memory`/`commit_memory`/`uncommit_memory`, implementadas sobre `mmap`/`mprotect` em POSIX) usadas sobretudo para o heap Java e o *code cache* do JIT.
- Threads nativas (`PlatformEvent`, base do `park`/`unpark` de toda concorrência Java, incluindo `Object.wait`/`notify` e `java.util.concurrent`) são implementadas sobre `pthread_mutex`+`pthread_cond`, não sobre *spinlocks*.
- O mecanismo de safepoint (ponto em que todas as threads Java param simultaneamente, necessário para GC e outras operações globais da VM) depende, na implementação mais comum, de uma página de memória que é despropositadamente protegida (`mprotect` sem permissão de acesso); quando uma thread Java executa sua instrução de *poll* periódica e toca essa página, a CPU gera uma falta de página, a VM intercepta via um handler de `SIGSEGV` instalado por ela mesma, e redireciona a execução para o código de safepoint — sem isso, a única alternativa é um polling explícito em software em cada ponto de segurança, mais lento.
- Há consulta de relógio (`clock_gettime` ou equivalente) e E/S de arquivo básica (`open`/`read`/`mmap` de arquivo) para carregar classes do *class path*.
- **Achado não previsto no roadmap original**: o HotSpot "de fábrica" é composto por múltiplas bibliotecas compartilhadas (`libjvm.so`, `libjava.so`, bibliotecas nativas de classes da biblioteca padrão), carregadas em tempo de execução via o linker dinâmico do sistema operacional (`dlopen`/resolução por *soname*), e o próprio JNI depende de `dlopen` para carregar bibliotecas nativas de aplicações de terceiros. Isso é um requisito de peso comparável a memória/threads/sinais, e não tem solução trivial num kernel sem um linker dinâmico de ELF.
- Esse requisito pode, em princípio, ser evitado por uma JVM totalmente estática (um único binário monolítico, sem `dlopen` em tempo de execução) — mas essa não é a configuração padrão do OpenJDK; é uma linha de trabalho experimental e incompleta mesmo no próprio projeto OpenJDK/Leyden (um teste recente de build totalmente estático ainda reportou dependências de `-lm -ldl -lpthread -lrt`, ou seja, nem os próprios autores do OpenJDK têm hoje uma receita completa e estável de build 100% estático).

## Goals / Non-Goals

**Goals:**
- Decidir formalmente a estratégia de portabilidade (opção 1 da seção 6 do documento de arquitetura): camada de compatibilidade POSIX mínima no kernel.
- Inventariar, com base em pesquisa real sobre a arquitetura interna do HotSpot, as primitivas que essa camada precisará oferecer no mínimo, e mapear cada uma contra o que o kernel já tem versus o que falta.
- Registrar o achado sobre carregamento dinâmico de bibliotecas como um risco explícito, sem fechar a decisão de como resolvê-lo agora.
- Delimitar a fronteira entre esta change (decisão + inventário, sem código) e a change futura do item 8 do roadmap (porte inicial da JVM, que implementa a camada de verdade).

**Non-Goals (nesta change):**
- Implementar qualquer parte da camada de compatibilidade POSIX no kernel — fica inteiramente para o item 8 do roadmap.
- Decidir a estratégia de linkagem (dinâmica vs. estática) do JDK/JVM final — registrado como risco em aberto, não como decisão.
- Escolher qual distribuição/versão específica do OpenJDK será portada, ou detalhes do processo de *bootstrap* de compilação cruzada do próprio OpenJDK para o Java OS — são decisões da change do item 8, não desta.
- Qualquer decisão sobre o modelo híbrido de execução de JVM (item 9 do roadmap, runtime compartilhado vs. JVM isolada por aplicação) — depende desta decisão, mas é tratada em sua própria change.

## Decisions

### Opção 1 (camada de compatibilidade POSIX mínima) é a estratégia adotada
Das três opções da seção 6 do documento de arquitetura, a opção 1 foi escolhida (decisão do usuário, registrada aqui): implementar no kernel um conjunto mínimo de primitivas com semântica POSIX, e portar o HotSpot sobre essas primitivas com o mínimo de modificação possível no seu próprio código-fonte (idealmente, tratando o Java OS como "mais um `os_<nome>`" dentro da estrutura já existente de `src/hotspot/os/<plataforma>` do HotSpot, análogo a como `os_linux`/`os_bsd` já existem).

**Por que não a opção 2** (porte direto das camadas de abstração de SO do próprio HotSpot para as primitivas nativas do kernel, sem POSIX intermediário): embora evite reimplementar semântica POSIX que o kernel não usa para mais nada, exigiria reescrever/adaptar individualmente cada ponto de uso de `os::` dentro do HotSpot para as primitivas nativas do Java OS — um acoplamento muito mais profundo com o código interno do HotSpot (que muda entre versões do OpenJDK) do que implementar uma camada POSIX fina e estável por baixo de um `os_<plataforma>` que já seria necessário de qualquer forma.

**Por que não a opção 3** (JVM alternativa minimalista para bootstrap): adiaria, não eliminaria, o problema do HotSpot completo (ou de qualquer runtime Java sério) rodar sobre o Java OS — e esta decisão de arquitetura precisa ser tomada agora, antes do item 8, não depois de um bootstrap paralelo que teria sua própria camada de compatibilidade diferente.

### Inventário de primitivas POSIX mínimas exigidas pelo HotSpot

| Primitiva POSIX | Uso no HotSpot | O que o kernel já tem | O que falta |
|---|---|---|---|
| `mmap`/`munmap` (reserva de memória virtual, sem necessariamente committar) | Heap Java, *code cache* do JIT, memória de metadados da VM (`os::reserve_memory`) | `kernel::paging::Mapper::map`/`map_new` mapeia página a página, já resolvida (sem conceito de "reservado mas não committado") | Uma API de reserva de uma faixa de endereço virtual sem alocar frame físico ainda, e de *commit* sob demanda de partes dela |
| `mprotect` (mudar permissões de uma página já mapeada) | Páginas de guarda, a página de polling de safepoint (ver abaixo) | `PageFlags` já existe no mapeamento inicial, mas não há API para alterar flags de uma página já mapeada sem desmapear/remapear | Uma API de "alterar permissões de uma página existente" |
| Criação de thread nativa (`pthread_create` e equivalentes) | Toda thread não-Java da VM (threads de compilação JIT, GC, etc.) além das threads Java propriamente ditas | `kernel::scheduler::spawn`/`spawn_sharing_current_address_space` já criam threads kernel, mas não há uma API pensada para ser chamada repetidamente por uma VM hóspede como "crie-me uma thread com esta função de entrada" de fora do próprio kernel | Uma API de criação de thread estável e própria para consumidores como uma JVM portada (possivelmente uma syscall nova, já que a JVM roda em modo usuário) |
| `pthread_mutex`/`pthread_cond` (base de `PlatformEvent`/`Parker`, ou seja, de `park`/`unpark`, `Object.wait`/`notify`, `java.util.concurrent`) | Toda sincronização entre threads Java | `kernel::sync::Spinlock` só faz exclusão mútua por *busy-wait*; não há primitiva de bloqueio/sono de thread em lugar nenhum do kernel ainda (nem para uso interno) | Uma primitiva real de bloqueio com fila de espera (a thread bloqueada sai da fila de escalonamento até ser acordada) — hoje inexistente mesmo para uso interno do kernel |
| Handler de sinal para `SIGSEGV` numa página protegida (polling de safepoint) + tratamento de erro fatal | Parar todas as threads Java simultaneamente para GC/operações globais da VM, sem polling explícito em cada ponto de segurança | `kernel/src/idt.rs` já tem `page_fault_handler` (vetor 14), mas hoje trata qualquer *page fault* como evento fatal — não existe mecanismo de "esta falta de página específica (endereço X) deve desviar a execução para um handler escolhido pelo processo que falhou, em vez de matar o processo" | Um mecanismo de registro, por processo, de "esta página gera um desvio para este handler em modo usuário" — análogo ao que `sigaction(SIGSEGV, ...)` faz em POSIX |
| Relógio monotônico e relógio de parede (`clock_gettime`) | Medição de tempo interna da VM, `System.nanoTime()`/`currentTimeMillis()` | `kernel::timer` já conta ticks desde o boot (usado pela segunda *syscall* existente) | Falta uma noção de tempo de parede real (hora do RTC) e uma resolução de tempo mais fina que o período do tick do escalonador, se necessário |
| E/S de arquivo básica (`open`/`read`/`mmap` de arquivo) | Carregar classes do *class path*, ler o próprio executável/bibliotecas da JVM | `kernel::storage`/`hal::BlockDevice` dão acesso a blocos brutos do disco; não há sistema de arquivos | Um sistema de arquivos (não previsto em nenhuma change ainda) é pré-requisito antes mesmo da camada POSIX poder expor `open`/`read` de verdade |
| Carregamento dinâmico de bibliotecas (`dlopen`) | `libjvm.so` carregando `libjava.so`; JNI carregando bibliotecas nativas de aplicações | Nada — não existe noção de biblioteca compartilhada nem linker dinâmico no kernel | Ver risco dedicado abaixo — não é só "uma primitiva faltando", é uma peça de infraestrutura inteira (linker de ELF dinâmico) ou uma mudança de estratégia de build (JDK estático) |

### Fronteira entre esta change e o item 8 do roadmap
Esta change entrega só a decisão e o inventário acima (sem código). A change do item 8 ("Porte inicial da JVM") é responsável por: decidir a forma concreta de cada primitiva da tabela acima (ex.: syscalls novas vs. extensão das existentes), implementá-las no kernel, e só então integrar um HotSpot (ou derivado) de fato. Em particular, a primitiva de bloqueio/sono de thread (hoje inexistente mesmo para uso interno do kernel) é provavelmente um pré-requisito tão fundamental que pode justificar sua própria sub-change antes do porte da JVM propriamente dito — mas essa divisão fica para o planejamento do item 8, não para esta change.

## Riscos / Trade-offs

- **[Risco] Carregamento dinâmico de bibliotecas (`dlopen`/linker de ELF) é um requisito do HotSpot "de fábrica" sem solução óbvia num kernel sem linker dinâmico** → Não mitigado nesta change (ver Non-Goals). Candidato mais promissor para avaliação na change do item 8: build totalmente estático do JDK (um único executável monolítico, sem `dlopen` em tempo de execução para as próprias bibliotecas do JDK) — mas isso é hoje uma linha de trabalho experimental e incompleta mesmo no projeto OpenJDK/Leyden (dependências residuais de `libm`/`libdl`/`libpthread`/`librt` reportadas em testes recentes), não uma receita pronta. Se um build 100% estático se provar inviável, a alternativa é implementar um linker dinâmico de ELF mínimo no kernel — uma peça de infraestrutura own right, não um detalhe da camada POSIX.
- **[Risco] Ausência de qualquer primitiva de bloqueio/sono de thread no kernel hoje (só *busy-wait* via `Spinlock`)** → É o maior gap estrutural identificado: sem ela, `park`/`unpark` (base de toda concorrência Java) não tem como ser implementado com uma semântica minimamente eficiente. Mitigação proposta: tratar como pré-requisito explícito da change do item 8, possivelmente como sua primeira sub-etapa.
- **[Risco] Ausência de sistema de arquivos** → Bloqueia `open`/`read` de verdade (necessário para carregar classes). Mitigação proposta: avaliar na change do item 8 se um sistema de arquivos mínimo (ainda que somente leitura) precisa vir antes, ou se um *classpath* embutido na imagem de boot (sem sistema de arquivos de verdade) é aceitável para a primeira JVM "hello world" do item 8, adiando o sistema de arquivos de verdade para uma change posterior.
- **[Trade-off] Camada POSIX fina em vez de um ambiente POSIX completo** → Aceito deliberadamente (é a essência da opção 1): a camada só precisa cobrir o que o HotSpot realmente usa, não ser um ambiente POSIX genérico utilizável por qualquer programa Unix não modificado.

## Migration Plan

Não aplicável — esta change não move nenhum estado nem altera nenhum código. "Deploy" desta change é a atualização de `docs/architecture/overview.md` (seção 6 com a decisão tomada e o inventário; item 7 do roadmap marcado como concluído). Nenhuma build/teste automatizado é afetado.

## Fontes consultadas

Pesquisa feita via busca na web (documentação pública da Oracle sobre o HotSpot, código-fonte espelhado do OpenJDK, e discussões arquivadas nas listas de e-mail do próprio projeto OpenJDK), já que não há como compilar/rodar o HotSpot de verdade neste ambiente de desenvolvimento:
- Documentação oficial Oracle sobre sinais e exceções no HotSpot (mecanismo de polling de safepoint via página protegida e `SIGSEGV`).
- Código-fonte espelhado de `src/hotspot/os/posix/os_posix.hpp`/`.cpp` e `src/hotspot/os/linux/os_linux.hpp`/`.cpp` (estrutura da camada `os`, `PlatformEvent`/`PlatformParker` sobre `pthread_mutex`/`pthread_cond`).
- Histórico de revisões (`webrev`) de `src/hotspot/share/runtime/os.hpp` ao longo de várias versões do OpenJDK (API pública de `reserve_memory`/`commit_memory`/`uncommit_memory` sobre hooks `pd_*` específicos de plataforma).
- Discussões arquivadas nas listas `hotspot-dev`/`bsd-port-dev`/`zero-dev` do OpenJDK sobre esforços anteriores de porte para novas plataformas (confirmando que a camada de SO concentra a maior parte do trabalho de porte fora da própria VM, e apontando a variante "Zero", sem código de máquina específico de arquitetura, como caminho mais simples para uma primeira integração).
- Relatos de bugs e discussões (`bugs.openjdk.org`, lista `leyden-dev`) sobre a dependência de `libjvm.so`/`libjava.so` em carregamento dinâmico via *soname*, e sobre o esforço experimental de build totalmente estático do JDK (`JDK-8303796`, projeto Leyden), incluindo o relato recente de dependências residuais de `libm`/`libdl`/`libpthread`/`librt` mesmo num build "estático".

Estas fontes documentam a estrutura e os requisitos gerais da camada `os` do HotSpot ao longo de várias versões; os nomes exatos de função/arquivo podem variar na versão específica do OpenJDK escolhida para porte na change do item 8, e deverão ser reconfirmados contra o código-fonte real naquele momento.
