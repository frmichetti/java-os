# Design

## Context

Hoje nenhuma IRQ de hardware externo chega à CPU: `kernel::pic::disable()` remapeia e mascara totalmente o PIC 8259 legado (chamada em `apic::init()`, antes de habilitar o Local APIC), e o único driver de interrupção existente, `kernel::apic`, só cobre o Local APIC em si (timer interno via LVT, EOI, vetor "spurious") — sem nenhum driver de I/O APIC. O timer funciona sem isso porque é gerado internamente pelo próprio Local APIC; um dispositivo externo como o teclado PS/2 (IRQ1) não tem esse caminho. `kernel::idt` já expõe `set_handler(vector, handler_addr, ist_index)` para registrar handlers específicos (usado pelo timer), com um handler padrão (`default_interrupt_handler`, que só dá EOI) ocupando todo o resto da faixa de hardware (vetores 32-255) até ser sobrescrito. `kernel::port` já expõe `inb`/`outb`. Ver `proposal.md` — Why/What Changes para a motivação completa, incluindo a lacuna de I/O APIC encontrada durante a investigação.

## Goals / Non-Goals

**Goals:**
- Um driver mínimo de I/O APIC capaz de rotear uma IRQ ISA específica (aqui, IRQ1) para um vetor da IDT entregue ao Local APIC.
- Um driver de teclado PS/2 (primeiro canal) funcional: inicialização do controlador 8042, tratamento de IRQ1, tradução de scancodes (set 1) para eventos de tecla com caractere ASCII, incluindo suporte básico a Shift (maiúsculas/símbolos).
- Uma abstração de HAL (`KeyboardDevice`) análoga ao `Console` já existente, e uma fila de eventos simples para quem for consumi-la.
- Uma demonstração mínima (thread de kernel que ecoa eventos recebidos nos consoles existentes), provando o mecanismo ponta a ponta — análoga ao `user_demo` de `kernel-syscalls`, mas em modo kernel (não há razão para modo usuário aqui).

**Non-Goals (nesta change):**
- Parsing de tabelas ACPI/MADT para descobrir dinamicamente o endereço do I/O APIC ou overrides de roteamento de IRQ — o endereço fixo padrão de plataforma PC-compatível é assumido (ver Decisões). Fica para quando o projeto precisar validar hardware real de verdade (item 12 do roadmap).
- Suporte a múltiplas CPUs/roteamento para um Local APIC específico por afinidade — o kernel ainda é single-core; a IRQ é roteada para o único Local APIC existente (o do BSP).
- Segundo canal PS/2 (mouse), teclado USB, múltiplos layouts configuráveis, teclas mortas/combinação de acentos, repetição automática de tecla (key repeat) configurável, Ctrl/Alt/CapsLock, teclas estendidas (as prefixadas por `0xE0`: setas, Insert/Delete, teclado numérico estendido, etc.) — todas ignoradas nesta primeira versão, sem travar nem corromper o estado do driver.
- Um shell/REPL interativo de verdade consumindo os eventos — a demonstração desta change só ecoa o que recebe, para provar o mecanismo; um consumidor real fica para uma change futura.

## Decisions

### I/O APIC: endereço MMIO fixo, sem parsing de ACPI/MADT
O endereço base do I/O APIC é assumido como `0xFEC00000` — o padrão de facto de qualquer plataforma PC-compatível (e o valor usado pelo I/O APIC emulado do QEMU, do VirtualBox e do VMware, os únicos alvos atuais do projeto por enquanto). Da mesma forma, assume-se que a IRQ1 (teclado) mapeia 1:1 para a entrada 1 da tabela de redireção do I/O APIC (GSI1), sem override — verdade em qualquer plataforma PC-compatível que não tenha uma entrada MADT "Interrupt Source Override" dizendo o contrário, o que não é o caso de nenhuma VM usada atualmente. Acesso via duas janelas MMIO de 32 bits mapeadas nesse endereço: `IOREGSEL` (offset `0x00`, seleciona o registrador) e `IOWIN` (offset `0x10`, lê/escreve o valor). Cada entrada da tabela de redireção ocupa dois registradores de 32 bits (baixo e alto), a partir do índice `0x10 + 2*irq`.

**Alternativa descartada**: parsear as tabelas ACPI (RSDP → RSDT/XSDT → MADT) para descobrir o endereço real do I/O APIC e qualquer override de roteamento. Correto para hardware real arbitrário, mas é uma quantidade substancial de código novo (parsing de tabelas, validação de checksum, iteração de entradas MADT) que esta change não precisa para atingir seu objetivo atual (QEMU/VirtualBox/VMware) — decisão confirmada com o usuário antes de escrever este design (ver proposal.md). Deixado como trabalho futuro explícito, junto do item 12 do roadmap ("Hardening multi-hardware").

### Entrada de redireção: modo físico, vetor fixo, destino = Local APIC ID do BSP
Cada entrada programada usa modo de entrega "Fixed", modo de destino físico, borda (edge-triggered) e polaridade ativa-alta (o padrão para qualquer IRQ de barramento ISA, incluindo IRQ1) e, no campo de destino, o Local APIC ID da própria CPU (lido via `kernel::apic`, nova função que lê o registrador de ID do x2APIC — MSR `0x802`). Como o kernel é single-core, o único Local APIC existente é sempre o do BSP; o campo de destino de 8 bits de uma entrada clássica de I/O APIC comporta sem problema o ID do BSP em qualquer uma das VMs alvo (tipicamente `0`).

**Alternativa descartada**: modo de destino lógico (broadcast por conjunto de CPUs via um registrador de destino lógico). Desnecessário e mais complexo para um único Local APIC; revisar quando SMP for adicionado.

### Teclado PS/2: inicialização mínima do controlador 8042, sem self-test exaustivo
A sequência de inicialização desabilita os dois canais PS/2 (comandos `0xAD`/`0xA7`), esvazia o buffer de saída (lê `0x60` enquanto o bit 0 do status em `0x64` estiver ligado), lê o byte de configuração do controlador (`0x20`), ajusta esse byte para habilitar a IRQ1 do primeiro canal (bit 0) e manter a IRQ12 do segundo canal desabilitada (fora de escopo), escreve o byte de volta (`0x60` seguido do byte), e reabilita só o primeiro canal (`0xAE`). Não executa o self-test do controlador (`0xAA`) nem o teste de porta (`0xAB`) — passos opcionais do protocolo 8042 que os controladores emulados de QEMU/VirtualBox/VMware não exigem para funcionar corretamente, e que adicionariam tratamento de timeout/falha sem benefício real no alvo atual.

**Alternativa descartada**: sequência de inicialização completa (self-test do controlador, teste de cada porta, detecção de controlador de canal único vs. duplo antes de decidir quais bits mexer). Mais robusta para hardware real variado, mas desproporcional ao escopo atual (só QEMU/VMs) — revisar junto da validação de hardware real (item 12 do roadmap), mesma lógica da decisão de I/O APIC acima.

### Scancodes: set 1, com estado de Shift, sem teclas estendidas
Scancodes são tratados como "set 1" (o formato clássico IBM PC/XT, que o controlador 8042 entrega por padrão após a tradução interna que ele já faz a partir do que o periférico realmente envia — o mesmo pressuposto universalmente feito por drivers de teclado PS/2 simples). Um *make code* tem o bit 7 zerado; o *break code* correspondente é o mesmo valor com o bit 7 ligado (`make_code | 0x80`). Duas tabelas fixas (`[Option<u8>; 128]`), uma para o caractere sem Shift e outra para o caractere com Shift, cobrem as teclas alfanuméricas e de símbolo do layout US QWERTY; o estado de Shift é um `bool` (ou dois, para esquerda/direita) atualizado pelos próprios make/break codes das teclas Shift, sem precisar aparecer como um evento de tecla "normal" por si (embora nada impeça: o Shift também tem seu próprio código ASCII `None`, então ainda pode gerar um evento sem caractere, útil para um consumidor futuro que precise saber que o Shift foi pressionado). Bytes de prefixo `0xE0` (teclas estendidas: setas, Insert/Delete/Home/End, teclado numérico estendido, etc.) são reconhecidos e o próximo byte é descartado sem gerar evento — simples o bastante para não corromper o estado do driver, mas sem tentar decodificar essas teclas (Non-Goal).

**Alternativa descartada**: scancode set 2 (o que o periférico PS/2 realmente envia internamente, antes da tradução do controlador) ou negociação dinâmica do set via comandos ao periférico (`0xF0` no canal de dados). Scancode set 1 pós-tradução é o comportamento padrão do controlador 8042 (bit de tradução do byte de configuração normalmente já vem ligado, inclusive nos controladores emulados das VMs alvo) e evita qualquer negociação adicional com o periférico.

### Fila de eventos: buffer circular de capacidade fixa, mesmo padrão de `Spinlock` já usado no kernel
Os eventos gerados pelo handler de IRQ1 são empilhados num buffer circular de capacidade fixa (32 entradas) protegido pelo mesmo `kernel::sync::Spinlock` já usado por `SERIAL1`/`CONSOLE`. Um evento gerado quando a fila já está cheia é descartado (o mais novo, não o mais antigo) — aceitável dado que a taxa de digitação humana é ordens de magnitude menor que a taxa de consulta esperada (um thread de kernel consultando em loop apertado, ou futuramente algo acordado a cada tick de 100 Hz do timer); documentado como limitação conhecida, mesma postura já adotada para o pool de stacks de thread em `kernel-process-scheduler`.

### HAL: `trait KeyboardDevice`, só `poll_event`, ao lado de `Console`
```rust
pub trait KeyboardDevice {
    fn poll_event(&mut self) -> Option<KeyEvent>;
}
```
Um método só, não-bloqueante (consistente com o kernel ainda não ter nenhuma primitiva de bloqueio/espera de thread) — devolve `None` quando não há evento pendente, em vez de bloquear a thread chamadora. `KeyEvent { pressed: bool, ascii: Option<u8> }` vive em `kernel::keyboard` (não em `kernel::hal`, mesmo padrão de `Console`/`FramebufferConsole` de `kernel-framebuffer-console`, cujos tipos concretos também vivem no módulo do driver, não na HAL). Um tipo zero-size `pub struct Ps2Keyboard;` implementa o trait delegando para a fila global.

### Demonstração: thread de kernel que ecoa eventos, reaproveitando `scheduler::spawn`
Igual ao `user_demo` de `kernel-syscalls`, mas em modo kernel (sem motivo para modo usuário aqui, já que não há syscall de teclado nem isolamento a provar): um módulo `kernel::keyboard_demo` com uma função `extern "C" fn run() -> !` que consulta `keyboard::poll_event()` em loop apertado e, a cada evento com caractere ASCII presente, imprime via `serial_println!` (já espelhado no framebuffer desde `kernel-framebuffer-console`) — ex.: `"tecla: 'a' (pressionada)"`. Criada via `scheduler::spawn(frame_allocator, keyboard_demo::run)`, chamada em `continue_boot` depois da inicialização do teclado, mesmo padrão de wiring já usado para o `user_demo`.

**Alternativa descartada**: integrar o polling direto em `idle_loop()` (`kernel::lib.rs`). Rejeitada por `idle_loop` ser uma função genérica de "halt ocioso de sucesso" usada no fim de qualquer sequência de boot bem-sucedida — acoplar lógica de teclado ali tornaria essa função específica de uma única change, quando já existe o mecanismo de thread de kernel exatamente para isso.

## Achados durante a implementação

- **Deadlock de single-core entre a thread de demonstração e o handler de IRQ1**: a implementação inicial de `keyboard::poll_event()` só travava `QUEUE` (`QUEUE.lock().pop()`), sem desabilitar interrupções durante a seção crítica. `kernel::keyboard_demo::run()` consulta `poll_event()` num loop bem apertado — havia uma chance real de a IRQ1 disparar exatamente enquanto essa thread já segurava o lock de `QUEUE`, e o handler (que roda "por cima" da thread interrompida, na mesma CPU) então travava para sempre esperando o mesmo lock, que a thread interrompida nunca mais executaria para liberar (só volta a rodar depois que o handler retornar). Encontrado via boot real: o sistema inteiro travava (CPU em ~95-100%, nenhuma saída nova) na primeira tecla recebida. Corrigido com a mesma técnica já usada por `kernel::scheduler` para `READY_QUEUE`/`CONTEXTS`/`PROCESSES` (`with_interrupts_disabled`, agora `pub(crate)` e reutilizada por `kernel::keyboard::poll_event`): desabilitar interrupções durante a seção crítica do lado consumidor, para que a IRQ1 nunca possa interromper exatamente no meio dela.

- **Página MMIO do I/O APIC não estava mapeada**: ao contrário do framebuffer do Limine (cujo endereço já vem como um ponteiro HHDM pronto), `0xFEC00000` é um endereço físico "cru" que o próprio kernel escolheu (ver "I/O APIC: endereço MMIO fixo" acima) — a HHDM do Limine só garante cobrir memória usável/reclamável pelo bootloader, não qualquer endereço físico arbitrário. A primeira tentativa de `route_irq` causava um page fault (`endereco=0xfec00000`, depois `0xffff8000fec00000` já com a tradução HHDM aplicada mas ainda sem mapeamento real). Corrigido com `kernel::ioapic::init(frame_allocator)`, que mapeia essa página explicitamente via `kernel::paging::Mapper` antes de qualquer uso de `route_irq` — mesmo `Mapper` já usado por `kernel::heap`/`kernel::stack`.

- **IRQ1 só era entregue uma vez por sessão de boot a 100 Hz (frequência padrão do escalonador) — achado mais custoso de diagnosticar desta change**: depois das duas correções acima, a primeira tecla simulada (via `sendkey`/QMP `input-send-event` do QEMU) chegava e era traduzida corretamente, mas nenhuma tecla seguinte (mesmo enviada minutos depois, em conexões de monitor totalmente separadas, ou via QMP com eventos de press/release explícitos) nunca mais disparava uma nova interrupção — sem travar o sistema (o timer e as outras threads continuavam rodando normalmente). Investigação extensiva via GDB remoto (`cargo xtask run -- -s -S`) e o comando `info lapic` do monitor do QEMU:
  - A entrada de redireção do I/O APIC para IRQ1 permanecia sempre saudável (não mascarada, sem delivery status pendente, sem remote IRR) — não era uma entrada "presa".
  - `info lapic` revelava o vetor do teclado permanentemente pendente em **IRR**, nunca promovido a **ISR** — ou seja, o Local APIC via o pedido, mas nunca o entregava à CPU.
  - Descartado como causa: prioridade do vetor da IDT (testado com o vetor do teclado na mesma classe do timer, em uma classe bem diferente, e até na prioridade mais alta possível, `0xF0`), o IMCR (portas 0x22/0x23, comutado para modo APIC), polaridade/modo de disparo (testado nível + ativo-baixo além de borda + ativo-alta), e o número de espaços de endereçamento em rotação a cada tick (reduzido de 3 para 2 fazendo `kernel::keyboard_demo` compartilhar o `CR3` da thread de boot via `kernel::scheduler::spawn_sharing_current_address_space`, em vez de `kernel::scheduler::spawn` — mantido no código por ser uma otimização legítima, mesmo não tendo resolvido sozinho).
  - O fator decisivo descoberto por bisseção foi a **frequência do timer do escalonador**: a 2 Hz e a 20 Hz, a IRQ1 era entregue de forma perfeitamente confiável (pressionar e soltar de várias teclas em sequência, incluindo Shift); só falhava na frequência padrão de 100 Hz.
  - **Confirmação definitiva**: rodando o mesmo binário, na mesma frequência de 100 Hz, com aceleração de hardware real (`-accel kvm -cpu host`, em vez da emulação por software via TCG usada em todo o resto deste projeto) — toda a sequência de teclas (pressionar/soltar de várias teclas, incluindo Shift) foi entregue perfeitamente. **Isso prova que o driver (roteamento via I/O APIC, driver PS/2, tradução de scancode, fila de eventos, HAL) está correto**; a falha a 100 Hz sob TCG é uma limitação de timing da emulação por software do QEMU sob alta frequência de interrupção concorrente, não um defeito do kernel.
  - Decisão: manter a frequência padrão do escalonador em 100 Hz (não vale a pena degradar a resolução de todo o escalonador para contornar uma limitação específica do ambiente de teste TCG) e documentar esta limitação conhecida — ver `KNOW_ISSUES.md`. A verificação de ponta a ponta desta change (tarefa 5.3) foi considerada bem-sucedida com base na confirmação via KVM; verificação visual adicional via `sendkey` sob TCG a 100 Hz pode mostrar só a primeira tecla, o que é esperado e não indica regressão.

## Riscos / Trade-offs

- **[Risco] Endereço fixo do I/O APIC e mapeamento 1:1 de IRQ1→GSI1 podem não valer em hardware real** → Mitigação: já documentado como Non-Goal explícito, revisão prevista junto do item 12 do roadmap (hardware real). Nenhuma das VMs alvo atuais (QEMU/VirtualBox/VMware) diverge disso.
- **[Risco] Sem self-test do controlador 8042, uma falha real de hardware/firmware atípico passaria despercebida** → Aceitável no alvo atual (VMs); mitigação futura junto da mesma revisão de hardware real.
- **[Risco] Handler de IRQ1 roda em contexto de interrupção, chamando `Spinlock::lock()`** → Mesmo padrão de risco já aceito e documentado para `SERIAL1`/`CONSOLE` (sem SMP, sem seção crítica longa, nenhum problema prático nesta fase); o handler só traduz um byte e empilha um evento, uma operação curta.
- **[Trade-off] Fila com descarte do evento mais novo quando cheia, em vez de bloquear o produtor ou crescer dinamicamente** → Aceitável: não há como o handler de IRQ bloquear (não há preempção dentro dele), e crescer dinamicamente exigiria alocação dentro de um handler de interrupção, isento de necessidade real dado o volume de eventos esperado.

## Migration Plan

Não há estado em produção. "Deploy" continua significando: `cargo test -p kernel --lib` continua passando sem regressão (os novos testes de host cobrem só lógica pura — tradução de scancode, estado de Shift, buffer circular), `cargo xtask test` (smoke test serial) continua passando sem nenhuma mudança de comportamento esperado, e uma verificação manual real em QEMU confirma a IRQ1 chegando e sendo traduzida corretamente — usando o comando `sendkey` do monitor do QEMU (a mesma técnica de automação via monitor já usada para o `screendump` de `kernel-framebuffer-console`) para injetar teclas simuladas e observar o eco nos consoles serial/framebuffer. Rollback é reverter os commits desta change; nenhum dado persistente é afetado.
