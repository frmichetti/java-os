- [x] 2.2 Implementar um contador de slots (`AtomicU64`, sem reciclagem — ver design.md Non-Goals) e `alloc_thread_stack(frame_allocator) -> Result<u64, StackInitError>` que aloca o próximo slot e devolve o endereço do topo. **Achado durante a tarefa 5.2 (boot real):** a primeira versão recebia um `root` e mapeava via `Mapper::for_root` sobre a address space (inativa) do processo da thread — como nada troca `CR3` para threads kernel-mode nesta change, isso deixava a stack mapeada numa PML4 que nunca está ativa, causando `#PF` na primeira escrita. ## 3. `kernel::process`: processo, thread e contexto

- [x] 3.1 Definir `Context` (estado salvo de uma thread entre trocas — o `rsp` salvo) e `ThreadId`/`ProcessId` (newtypes sobre `u64`) em `kernel/src/process.rs`; registrado o módulo em `kernel/src/lib.rs`. Verificado que `cargo build`/`cargo kernel-build` compilam.
- [x] 3.2 Implementar a síntese do "trap frame" inicial de uma thread nova (`init_stack(stack_top, entry) -> u64`). **Dois achados sucessivos sobre o tamanho do frame de hardware:** a primeira versão presumiu 3 campos (RIP, CS, RFLAGS), por analogia com o modo protegido de 32 bits sem IST/troca de privilégio. Isso compilou e passou nos testes de host, mas falhou em boot real (tarefa 5.2): `iretq` em modo 64 bits sempre consome os 5 campos completos (RIP, CS, RFLAGS, RSP, SS), mesmo sem IST/troca de privilégio — confirmado via GDB (`#PF` na própria instrução `iretq`, lendo além do fim da stack mapeada). Corrigido para escrever os 5 campos, com o próprio campo `RSP` do frame carregando o valor de alinhamento de ABI (`stack_top - 8`), em vez de um pad separado. `design.md` corrigido para registrar essa precisão. Verificado com teste unitário em host (`init_stack_writes_expected_synthetic_trap_frame`, usando um `Vec<u8>` no lugar da stack real) que RIP/CS/RFLAGS/RSP/SS e o `rsp` salvo devolvido batem com os valores esperados; e em boot real (tarefa 5.2/6.1) que uma thread sintetizada começa a executar corretamente e sobrevive a múltiplas trocas de contexto.
- [x] 3.3 Implementar `Process::new(frame_allocator, entry) -> Result<(Process, Thread), ProcessError>` (cria `AddressSpace` + primeira `Thread`) e `Process::spawn_thread(&mut self, frame_allocator, entry) -> Result<Thread, ProcessError>` (nova stack/contexto na mesma `AddressSpace` do processo). Verificado que `cargo build`/`cargo kernel-build` compilam e que os IDs sucessivos de processo/thread são distintos (teste unitário em host); o restante é exercitado em boot real na tarefa 6.1.

## 4. `kernel::scheduler`: fila de prontos e troca de contexto

- [x] 4.1 Implementar a fila de prontos (`ReadyQueue`, uma `VecDeque<ThreadId>` circular) protegida por `Spinlock` em `kernel/src/scheduler.rs`, com toda seção crítica sobre ela (e sobre `CONTEXTS`/`PROCESSES`) rodando com interrupções desabilitadas via `with_interrupts_disabled` (salva/restaura `IF` em torno do lock — ver design.md). A seleção round-robin (`ReadyQueue::advance`, que devolve `(quem estava rodando, quem roda a seguir)`) é lógica pura, verificada com 3 testes unitários em host: fila de uma thread sempre devolve a si mesma, round-robin visita todas antes de repetir, fila vazia devolve `None`.
- [x] 4.2 Implementar `register_boot_thread()` (thread de boot, `continue_boot`, recebe o primeiro `ThreadId`/`ProcessId` do espaço monotônico de `kernel::process` — na prática `ThreadId(0)`, já que é sempre a primeira chamada) e `scheduler::spawn(frame_allocator, entry)` como wrapper sobre `Process::new` que registra a thread e retém o `Process` (incluindo sua `AddressSpace`) em `PROCESSES`, para não vazar a única referência à address space do processo (achado durante a implementação: descartar o `Process` logo após criar a thread impediria `spawn_thread`/inspeção futura da address space, necessária na tarefa 6.2). Verificado que `cargo build`/`cargo kernel-build` compilam.
- [x] 4.3 Implementar `on_timer_tick(current_rsp: u64) -> u64`: mantém o incremento do contador de ticks e o EOI (movidos para `kernel::timer::on_tick()`, reusável fora do antigo handler `extern "x86-interrupt"`), salva `current_rsp` no `Context` da thread corrente, escolhe a próxima via `ReadyQueue::advance` (4.1, sem duplicação de lógica), e devolve o `rsp` salvo dela. Verificado com `cargo test -p kernel --lib`; os testes existentes de `kernel-timer` continuam cobrindo o contador/calibração, inalterados.
- [x] 4.4 Escrever a rotina de entrada do timer (`timer_entry`, via `core::arch::global_asm!` + `#[unsafe(no_mangle)]` em `on_timer_tick`, não uma função `naked`, para manter o mesmo estilo explícito já usado em `kernel::stack::switch_to`) e apontar `idt::set_handler(TIMER_VECTOR, ...)` (em `kernel::timer::init`) para `scheduler::timer_entry_addr()` em vez do handler `extern "x86-interrupt"` antigo (removido). **Achado importante durante a implementação, não previsto em design.md:** uma interrupção pode chegar com `RSP` em qualquer alinhamento (não necessariamente múltiplo de 16), mas a ABI System V exige `RSP % 16 == 0` imediatamente antes de um `call` — a rotina precisa forçar esse alinhamento (`and rsp, -16`) logo antes de chamar `on_timer_tick`, descartando esse valor (nunca mais necessário, já que a stack é trocada logo depois); `design.md` atualizado registrando esse detalhe. Como a troca de contexto real só é verificável em hardware, verificado que `cargo build`/`cargo kernel-build` compilam; o comportamento é verificado em boot real nas tarefas 5.2 e 6.1.

## 5. Integração em `kernel_main`/`continue_boot`

- [x] 5.1 Em `continue_boot`, depois do timer já configurado e antes de `idle_loop()`, chamar `scheduler::register_boot_thread()` e logar a confirmação. Verificado com `cargo xtask test`: banner, memmap, heap, APIC, timer e "escalonador: iniciado (thread de boot registrada)" todos presentes no log serial; o boot completa normalmente mesmo com o timer já disparando repetidamente contra a nova rotina de troca de contexto (caso trivial de uma única thread round-robin consigo mesma), sem travar nem reiniciar.
- [x] 5.2 Adicionado temporariamente (mesmo padrão já usado para verificar a guard page em `kernel-stack-guard-page`) duas threads de teste via `scheduler::spawn`, cada uma incrementando seu próprio contador atômico num laço que nunca cede o controle. **Dois bugs reais encontrados e corrigidos em boot real antes da verificação passar:**
  1. `alloc_thread_stack` mapeava a stack da thread via `Mapper::for_root` sobre a PML4 (inativa) do processo recém-criado — mas nada troca `CR3` para threads kernel-mode nesta change, então a escrita do trap frame sintético (`init_stack`) faltava imediatamente (a stack não existia na PML4 realmente ativa). Corrigido voltando `alloc_thread_stack` a usar `Mapper::new` (a paginação ativa), consistente com o próprio racional de "stack de thread é compartilhada" já escrito em design.md — `Mapper::for_root` continua existindo para uso futuro em mapeamentos específicos de processo (tarefa 6.2).
  2. Com o primeiro bug corrigido, um `#PF` na própria instrução `iretq` revelou que o frame de hardware em modo 64 bits tem 5 campos (RIP, CS, RFLAGS, RSP, SS), não 3 como `design.md`/tarefa 3.2 presumiam — `design.md` e `kernel::process::init_stack` corrigidos (ver tarefa 3.2, atualizada).
  
  Depois das correções, log serial confirmou os dois contadores avançando intercalados (`thread de teste A`/`B`, crescendo juntos) — prova de escalonamento preemptivo real, sem cooperação, cobrindo os dois cenários de "Escalonamento Preemptivo Round-Robin" de `specs/kernel-scheduler/spec.md`. Código de teste temporário removido após a verificação; `cargo xtask test`/`cargo test -p kernel --lib` confirmados passando sem ele.
