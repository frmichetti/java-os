# Design

## Context

Hoje (pós `kernel-process-scheduler`) o kernel já tem processos com espaço de endereçamento próprio, threads com stack protegida por guard page e contexto de registradores, e um escalonador preemptivo round-robin cuja troca de contexto usa um "trap frame" na própria stack da thread, restaurado via `iretq` (ver `kernel::process::init_stack`, `kernel::scheduler`). Tudo roda em anel 0. `kernel::paging::PageFlags` já tem um campo `user_accessible` (usado para montar a flag `PTE_USER` de uma entrada de página), mas nenhum código até hoje o usa com `true`. O GDT (`kernel::gdt`) só declara segmentos de código/dados de kernel e o TSS; `TSS.rsp0` nunca foi escrito (sempre zero). Não existe carregador de executáveis (ELF ou qualquer outro formato) — só é possível criar uma thread a partir de uma função Rust já linkada no próprio binário do kernel.

Ver `proposal.md` — Why/What Changes para a motivação e o escopo; `specs/kernel-user-mode`, `specs/kernel-syscalls`, e os deltas de `specs/kernel-processes`/`specs/kernel-scheduler` para os requisitos.

## Goals / Non-Goals

**Goals:**
- Uma thread poder executar seu código em anel 3, com stack de usuário própria, sem acesso a memória exclusiva do kernel.
- Uma interface `syscall`/`sysret` funcional: uma thread de usuário consegue pedir um serviço ao kernel e retomar a execução em modo usuário com o resultado.
- Uma convenção de ABI (registradores para número/argumentos/retorno) e um mecanismo de despacho por número de chamada, com rejeição explícita de números inválidos.
- Duas chamadas de sistema reais (escrita no console, consulta do contador de ticks) suficientes para provar o mecanismo ponta a ponta — incluindo passagem de dados do usuário para o kernel e devolução de um valor do kernel para o usuário.

**Non-Goals (nesta change):**
- Carregamento de executáveis (ELF ou qualquer formato) — o programa de teste em modo usuário é gerado em tempo de compilação (`global_asm!`) e copiado manualmente para uma página de usuário em tempo de execução (ver Decisões). Um carregador real fica para quando houver um sistema de arquivos (roadmap item 6+).
- Isolamento/recuperação de falhas em modo usuário — uma exceção (page fault, `#GP`) causada por uma thread de usuário continua haltando o kernel inteiro, exatamente como hoje; encerrar apenas a thread/processo ofensor exigiria suporte a encerramento de thread, que `kernel-process-scheduler` já deixou como Non-Goal.
- Múltiplos núcleos (SMP) — permanece fora de escopo (roadmap item 12). Isso simplifica genuinamente esta change: a stack de kernel confiável para transições de privilégio pode ser uma única variável global (ver Decisões), sem precisar do mecanismo de dado-por-CPU (`swapgs`/`GS_BASE`) que um kernel SMP exigiria.
- Mais de duas chamadas de sistema, permissões por chamada, ou uma ABI estável/versionada — a convenção definida aqui é deliberadamente mínima, pensada para ser estendida depois sem redesenho.
- Múltiplos programas de usuário rodando simultaneamente ou comunicação entre eles — um único processo/thread de teste em modo usuário é suficiente para validar o mecanismo.

## Decisions

### Layout do GDT para `syscall`/`sysret`
A instrução `syscall` usa o MSR `STAR` para determinar os seletores de CS/SS tanto na entrada (`syscall`) quanto na saída (`sysret`), com uma regra de aritmética fixa definida pelo hardware (SDM Vol. 2, `SYSCALL`/`SYSRET`): com `K = STAR[47:32]` e `U = STAR[63:48]`,
- `syscall`: `CS = K`, `SS = K + 8`
- `sysret` (64 bits): `CS = (U + 16) | 3`, `SS = (U + 8) | 3`

Isso impõe uma ordem específica no GDT. Com `K = KERNEL_CODE_SELECTOR` (`0x08`), `SS` na entrada da syscall cai em `0x10` — exatamente `KERNEL_DATA_SELECTOR`, já existente, sem precisar de nenhuma entrada nova para o caminho de entrada. Para a saída, escolhendo `U = 0x10` (o mesmo valor numérico do seletor de dados do kernel, usado aqui só como base aritmética, não como um segmento real), as duas novas entradas de usuário precisam ficar em `U + 8 = 0x18` (dados) e `U + 16 = 0x20` (código) — ou seja, **dados de usuário antes de código de usuário**, ao contrário da ordem código-antes-de-dados já usada para o kernel. GDT final: `null(0x00)`, `kernel_code(0x08)`, `kernel_data(0x10)`, `user_data(0x18)`, `user_code(0x20)`. Essa é a mesma convenção (um tanto contraintuitiva, e por isso documentada aqui em detalhe) usada por praticamente todo kernel x86-64 que suporta `syscall`/`sysret` — ver OSDev Wiki, "SYSCALL/SYSRET".

**Alternativa descartada**: usar `iretq`/gates de interrupção comuns para implementar chamadas de sistema (via uma instrução `int`), em vez de `syscall`/`sysret`. Mais simples de entender (reaproveitaria o mesmo mecanismo já usado pelas exceções de CPU), mas significativamente mais lento (uma `int` consulta a IDT e faz mais verificações de proteção do que `syscall`, que foi desenhada especificamente para esse caso) — o próprio roadmap já especifica `syscall`/`sysret` "por desempenho".

### Stack de kernel confiável: uma única variável global (sem `swapgs`)
`syscall` **não troca `RSP` automaticamente** — ao contrário de um gate de interrupção com troca de privilégio (que usa `TSS.rsp0` via hardware), `syscall` entrega o controle ao kernel ainda sobre a stack de usuário (não confiável) da thread chamadora. A rotina de entrada precisa trocar para uma stack de kernel confiável antes de tocar qualquer dado do usuário. Em um kernel SMP, isso normalmente exige `swapgs` + uma área de dados por-CPU; como este kernel é single-core (ver Non-Goals), basta uma única variável global `CURRENT_KERNEL_STACK_TOP: u64`, atualizada pelo escalonador a cada troca de contexto (a mesma troca que já acontece a cada tick do timer, generalizada para também acontecer na entrada/saída de uma `syscall`) — não há como dois núcleos divergirem sobre "qual é a thread corrente" porque só existe um núcleo.

A mesma variável (ou uma equivalente) também alimenta `TSS.rsp0`: como uma interrupção comum (ex.: o timer) que chega enquanto uma thread de usuário está rodando **usa**, sim, a troca automática de stack via `TSS.rsp0` (diferença chave entre gates de interrupção e `syscall` — ver próxima decisão), `TSS.rsp0` precisa estar sempre coerente com a thread corrente, não só no caminho de `syscall`.

**Alternativa descartada**: implementar a infraestrutura de dado-por-CPU (`swapgs`, `GS_BASE` via MSR) desde já, pensando em SMP futuro. Rejeitada por adicionar complexidade real sem nenhum benefício observável hoje (kernel genuinamente single-core); fica registrado aqui como o ponto exato que precisará mudar quando SMP for implementado (roadmap item 12).

### `TSS.rsp0` atualizado a cada troca de contexto, não só em `syscall`
Diferente de `syscall`, um gate de interrupção comum (ex.: o vetor do timer) **com troca de privilégio** (anel 3 → anel 0) faz a CPU trocar `SS:RSP` automaticamente para o valor em `TSS.rsp0`, empilhando aí o frame de 5 campos de sempre. Isso significa que, para uma thread de usuário ser interrompida com segurança pelo timer, `TSS.rsp0` já precisa estar correto *antes* da interrupção acontecer — não dá para esperar e corrigi-lo só dentro do handler. Por isso, `kernel::scheduler` passa a escrever `TSS.rsp0` (com o topo fixo da stack de kernel da nova thread corrente — um valor novo, `kernel_stack_top`, diferente do `Context::rsp` já existente, que flutua a cada troca) em **toda** troca de contexto, não apenas no caminho de `syscall`. Isso modifica `kernel-scheduler` (ver spec delta) e estende `Context`/`Thread` em `kernel-processes` com esse campo adicional, fixo desde a criação da thread.

### ABI de syscall: convenção inspirada no Linux x86-64, adaptada ao mínimo necessário
`syscall` sempre sobrescreve `RCX` (com o RIP de retorno) e `R11` (com `RFLAGS`), então esses dois registradores não podem carregar argumentos. Convenção adotada: número da chamada em `RAX`; até quatro argumentos em `RDI`, `RSI`, `RDX`, `R10` (não `RCX`, pela razão acima — mesma adaptação que o próprio Linux faz); valor de retorno em `RAX`. Um número de chamada não reconhecido devolve um valor de erro sentinela (ex.: `u64::MAX`) em `RAX`, nunca executa um serviço arbitrário.

### Thread de usuário: reaproveita o mecanismo de troca de contexto já existente
Entrar em modo usuário pela primeira vez é tratado como só mais um caso do mecanismo de "trap frame sintético" já usado por `kernel::process::init_stack` (ver design.md de `kernel-process-scheduler`): a única diferença é que `CS`/`SS` do frame apontam para os seletores de usuário (com RPL 3) em vez dos de kernel, e `RSP` do frame aponta para o topo da stack *de usuário* da thread, não da stack de kernel. A rotina de troca de contexto em si (empilhar/desempilhar registradores, `iretq`) não precisa de nenhuma mudança — `iretq` já lida com a troca de anel automaticamente a partir do RPL codificado em `CS`, propriedade já confirmada durante `kernel-process-scheduler`. Uma thread de usuário continua tendo sua própria stack de *kernel* (do pool já existente) — é para ela que `TSS.rsp0` aponta, e é nela que a rotina de entrada de `syscall`/interrupção salva o estado da thread.

**Alternativa descartada**: um caminho de inicialização totalmente separado para threads de usuário. Rejeitada por duplicar lógica já correta e testada (o trap frame sintético), quando a única diferença real está em quais valores de `CS`/`SS`/`RSP` são escritos nele.

### Primeiro programa de usuário: bytes de máquina gerados em compilação, copiados para uma página de usuário em runtime
Sem carregador de executáveis, o "programa" de teste em modo usuário é escrito como uma rotina `global_asm!` própria (mesmo padrão já usado para `scheduler::timer_entry`), deliberadamente **independente de posição** (sem referências a endereços absolutos do kernel) — só usa `syscall` e registradores. Em tempo de execução, seus bytes (do início até um rótulo de fim correspondente) são copiados para uma página recém-mapeada com `PageFlags { user_accessible: true, executable: true, .. }` na metade inferior do espaço de endereçamento de um processo, e a thread de teste é criada com `RIP` apontando para essa página (não para o endereço original da rotina dentro do kernel). Isso prova o mecanismo completo (modo usuário + `syscall`) sem precisar de nenhum formato de executável nem de armazenamento em disco.

**Dois achados sucessivos ao implementar isso contra hardware real, ambos reaparições/variações do mesmo princípio ("mapear numa PML4 inativa não a torna acessível pela PML4 realmente ativa"), já visto uma vez em `kernel-process-scheduler` para o pool de stacks de thread:**

1. **A própria cópia dos bytes do programa não podia escrever em `USER_DEMO_CODE_VIRT` diretamente.** A página de código é mapeada via `Mapper::for_root` na PML4 do *novo* processo — que só se torna ativa quando o escalonador escolher essa thread pela primeira vez. Escrever diretamente no endereço virtual final, antes dessa troca, falta (a paginação ativa no momento da cópia ainda é a do processo de boot). Corrigido copiando os bytes através do alias físico-direto (HHDM) do frame recém-alocado (devolvido por `map_new`) — válido independentemente de qual PML4 está ativa — em vez do endereço virtual final; a thread só usa esse endereço final como `RIP`, e ele só precisa estar correto quando ela realmente executar (depois da troca de `CR3`, ver próximo achado).

2. **Nada jamais trocava `CR3` entre processos.** A troca de contexto (`on_timer_tick`) já herdada de `kernel-process-scheduler` nunca chamava `AddressSpace::switch` — inofensivo enquanto só existiam threads de kernel (cuja metade superior, única que tocam, é idêntica em toda `AddressSpace`), mas uma thread de usuário tem mapeamentos próprios (código, stack) só visíveis na *sua* PML4. Corrigido: `Context` passa a guardar também `address_space_root` (capturado da PML4 ativa para a thread de boot, e de `AddressSpace::root()` para toda thread criada via `Process`), e `on_timer_tick` troca `CR3` para esse valor a cada troca de contexto, incondicionalmente (mesmo quando, por ora, o valor não muda — mais simples e seguro do que rastrear "mudou ou não", e o custo é desprezível nesta fase).

3. **Mesmo depois de corrigir (1) e (2), um terceiro problema (mais sutil) apareceu: a stack de *kernel* da própria thread de usuário ficava inacessível depois da troca de `CR3`.** Causa: `AddressSpace::new()` copia as entradas de PML4 **por valor**, no instante em que é chamada. O índice de PML4 do pool de stacks de thread (`kernel::stack::THREAD_STACK_POOL_BASE`) nunca tinha sido tocado antes (nenhuma thread havia sido criada ainda), então, no momento em que o processo de demonstração foi criado (`Process::begin_new_user`, antes de sua própria stack de kernel ser alocada), a cópia registrou esse índice como "ausente". A alocação da stack de kernel da thread (que acontece *depois*, dentro de `create_user_thread`) criou a tabela intermediária só na PML4 ativa (a do processo de boot) — sem "voltar" a ser compartilhada com a cópia já feita. Resultado: ao trocar para a PML4 do processo de demonstração (achado 2, acima), a stack de kernel dessa própria thread virava inacessível. Corrigido com `kernel::stack::prime_thread_stack_pool`, chamada uma única vez, bem cedo no boot, **antes** de qualquer `AddressSpace::new()` — mapeia e desmapeia imediatamente uma página de disfarce dentro do pool, só para forçar a cadeia PDPT/PD/PT a existir na PML4 ativa (a tabela intermediária criada como efeito colateral do mapeamento persiste mesmo depois do desmapeamento, que só remove a entrada-folha). **Limitação aceita:** isso cobre só a primeira PT do pool (~30 slots, dado que uma PT cobre 2 MiB e cada slot usa `SLOT_STRIDE` ≈ 68 KiB) — crescer o pool além disso reintroduziria o mesmo problema para a PT seguinte, a menos que viesse a ser pré-aquecida também. Aceitável no escopo atual (poucas threads); revisitar com uma solução mais geral (ex.: pré-criar toda a região reservada, ou documentar como obrigação de qualquer nova região compartilhada) se/quando o número de threads crescer de verdade.

Os três achados, em conjunto, generalizam para um princípio único que vale a pena guardar para qualquer change futura que crie `AddressSpace`s: **qualquer mapeamento na metade superior (compartilhada) só é visto por uma `AddressSpace` se a tabela intermediária correspondente já existisse na PML4 ativa no momento em que essa `AddressSpace` foi criada** — criar ou popular uma tabela intermediária compartilhada *depois* disso não se propaga retroativamente para cópias já feitas.

## Riscos / Trade-offs

- **[Risco] `syscall`/`sysret` é historicamente uma das áreas mais propensas a erro sutil de toda a arquitetura x86-64 (ex.: a classe de vulnerabilidade de `sysret` com RIP não-canônico, CVE-2012-0217-like)** → Mitigação: o valor de retorno usado por `sysret` é sempre o `RCX` que a própria `syscall` capturou do RIP de chamada real (nunca um valor fabricado ou derivado de entrada do usuário), o que evita a classe mais comum desse problema; ainda assim, verificar em boot real via GDB que o primeiro `syscall`/`sysret` de teste preserva corretamente `RIP`/`RFLAGS`/registradores do programa de usuário, com o mesmo rigor usado para validar a troca de contexto em `kernel-process-scheduler`.
- **[Risco] Esquecer de atualizar `TSS.rsp0` em algum caminho de troca de contexto deixa uma interrupção ou `syscall` futura usar uma stack de kernel errada (de outra thread) — corrupção silenciosa de stack, pior ainda que o bug de guard page original** → Mitigação: centralizar a atualização de `TSS.rsp0` num único ponto dentro da função de troca de contexto já existente (`on_timer_tick`/equivalente para `syscall`), nunca duplicado; verificar explicitamente em boot real com GDB que `TSS.rsp0` bate com a stack de kernel da thread corrente em múltiplos pontos ao longo da execução.
- **[Trade-off] Stack de kernel confiável como variável global única (sem dado-por-CPU)** → Aceitável e mais simples enquanto o kernel for single-core (Non-Goal de SMP); documentado como o ponto exato a revisar quando SMP chegar.
- **[Trade-off] Programa de usuário de teste como bytes copiados manualmente, não um executável real** → Aceitável para provar o mecanismo; carregar um executável real de verdade exigirá um formato (ELF ou outro) e armazenamento, nenhum dos dois ainda implementado.

## Migration Plan

Não há estado em produção. "Deploy" continua significando: o smoke test de boot (`cargo xtask test`) passa com o kernel reportando a configuração de `syscall` (MSRs, GDT de usuário), os testes unitários da lógica pura (convenção de ABI, despacho por número de chamada, aritmética da layout do GDT, quando aplicável) passam em host, e uma verificação manual via GDB confirma pelo menos um ciclo completo de `syscall`/`sysret` a partir do programa de teste em modo usuário — incluindo a chamada de escrita (visível no log serial) e a de consulta de ticks (valor devolvido corresponde ao contador real) — antes de qualquer tarefa relacionada ser marcada concluída. Rollback é reverter os commits desta change; nenhum dado persistente é afetado.
