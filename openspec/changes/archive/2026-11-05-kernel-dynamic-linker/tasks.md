# Tasks

## 1. Reaproveitamento de `kernel::elf` para objetos `ET_DYN`

- [x] 1.1 Estender `ElfHeader` (`kernel/src/elf.rs`) com o campo `e_type: u16`, e `ElfHeader::parse` para aceitar `e_type == ET_EXEC` **ou** `ET_DYN` (constante nova `ET_DYN: u16 = 3`), continuando a rejeitar qualquer outro tipo com `ElfError::UnsupportedExecutable` — verificar com `cargo test -p kernel --lib` cobrindo aceitação de `ET_DYN` e rejeição de um terceiro tipo (ex. `ET_REL`)
- [x] 1.2 Adicionar, em `kernel::scheduler::spawn_from_elf`, uma checagem explícita `header.e_type == ET_EXEC` (novo `ElfError`/variante reaproveitada) logo após `ElfHeader::parse`, preservando o comportamento hoje coberto pela spec `kernel-elf-loader` (rejeitar `ET_DYN` com o mesmo erro de antes) — verificar que os testes de host existentes de `kernel-elf-loader` continuam passando sem alteração e que `cargo xtask test` (smoke test) continua passando
- [x] 1.3 Implementar `kernel::elf::rebase_segments(segments: &[ProgramHeader], base: u64) -> Vec<ProgramHeader>` (função pura: soma `base` a `p_vaddr` de cada entrada, preservando os demais campos) — verificar com teste unitário comparando o resultado para uma base não-zero contra os segmentos originais

## 2. Parsing puro da seção dinâmica e da tabela de símbolos

- [x] 2.1 Criar `kernel/src/dylib.rs` com `enum DylibError` cobrindo, pelo menos: formato/tipo não suportado, seção dinâmica ausente ou fora dos limites, tag obrigatória ausente (`DT_STRTAB`/`DT_SYMTAB`/`DT_HASH`), hash GNU-only não suportado, segmento de relocação fora dos limites, tipo de relocação não suportado, símbolo não resolvido, dependência não encontrada, dependência circular, handle inválido, biblioteca maior que o slab reservado, falha de mapeamento/memória, disco/sistema de arquivos indisponível
- [x] 2.2 Implementar `find_dynamic_segment(buf: &[u8], header: &ElfHeader) -> Result<(usize, usize), DylibError>` (varre os program headers à procura do primeiro `PT_DYNAMIC`, devolve o intervalo de bytes em `buf` dessa tabela, com os mesmos limites verificados de `kernel::elf::load_program_headers`) — verificar com teste unitário usando um ELF sintético com um `PT_DYNAMIC` e sem nenhum
- [x] 2.3 Implementar `vaddr_to_file_offset(segments: &[ProgramHeader], vaddr: u64) -> Option<usize>` (encontra o segmento `PT_LOAD` original — sem rebase — que contém `vaddr` e devolve o deslocamento correspondente no arquivo) — verificar com teste unitário cobrindo um endereço dentro de um segmento e um fora de todos
- [x] 2.4 Implementar o parsing da tabela `.dynamic` (entradas de 16 bytes, `d_tag`/`d_val`, terminada em `DT_NULL`) extraindo `DT_NEEDED` (lista de deslocamentos em `.dynstr`), `DT_STRTAB`, `DT_SYMTAB`, `DT_HASH`, `DT_RELA`/`DT_RELASZ`, `DT_JMPREL`/`DT_PLTRELSZ`/`DT_PLTREL` — rejeitando com `DylibError` qualquer tag obrigatória ausente e qualquer `DT_PLTREL` diferente de `DT_RELA` — verificar com teste unitário usando uma tabela `.dynamic` sintética completa e uma com uma tag obrigatória faltando
- [x] 2.5 Implementar leitura de string C terminada em `\0` dentro de `.dynstr` dado um deslocamento, e resolução de cada `DT_NEEDED` para seu nome — verificar com teste unitário
- [x] 2.6 Implementar a contagem de símbolos via os dois primeiros `u32` de `DT_HASH` (`nbucket`/`nchain`, usando só `nchain`) e o parsing de `.dynsym` (`nchain` entradas de 24 bytes: `st_name`/`st_value`/`st_shndx`) — verificar com teste unitário que `nchain` incorreto/tabela truncada é rejeitado como `DylibError`, nunca indexado fora dos limites
- [x] 2.7 Implementar a extração da lista de símbolos exportados (`st_name != 0 && st_shndx != 0`, nome resolvido via `.dynstr`, endereço final = `st_value + base`) — verificar com teste unitário cobrindo um símbolo exportado e um de referência externa (`st_shndx == 0`, não deve aparecer na lista)

## 3. Parsing puro de relocações e resolução de símbolo

- [x] 3.1 Implementar o parsing de uma tabela de relocações `Elf64_Rela` (entradas de 24 bytes: `r_offset`, `r_info` decomposto em tipo/índice de símbolo, `r_addend`) para `DT_RELA`/`DT_JMPREL` — verificar com teste unitário decompondo `r_info` em tipo e índice de símbolo conhecidos
- [x] 3.2 Implementar `resolve_relocation_value(reloc, base, resolve_symbol: impl Fn(u32) -> Option<u64>) -> Result<u64, DylibError>` (função pura: `R_X86_64_RELATIVE` → `base + addend`; `GLOB_DAT`/`JUMP_SLOT`/`R_X86_64_64` → `resolve_symbol(indice) + addend`, propagando `None` como símbolo não resolvido; qualquer outro tipo → `UnsupportedRelocationType`) — verificar com teste unitário para cada tipo suportado e um não suportado, usando uma função de resolução de símbolo falsa (closure) para não depender de mapeamento real

## 4. Carregamento real de uma biblioteca e estado por espaço de endereçamento

- [x] 4.1 Implementar `ProcessDylibState { libraries: Vec<LoadedLibrary>, next_base: u64 }` e `static DYLIB_STATE: Spinlock<BTreeMap<u64, ProcessDylibState>>`, chaveada pelo `root` (`kernel::paging::current_root()`) — ver design.md, "Estado por espaço de endereçamento via `current_root()`" — com `LoadedLibrary { base: u64, symbols: Vec<(String, u64)> }`
- [x] 4.2 Implementar `load_library<S: FrameStore>(frame_allocator, fs: &Fat32Filesystem, path: &str, loading_stack: &mut Vec<String>) -> Result<usize, DylibError>`: detecta ciclo (`path` já em `loading_stack` → `DylibError::CircularDependency`), lê o arquivo, valida `ET_DYN` (tarefa 1.1), reserva uma base nova (bump de `next_base` por um slab fixo, documentado em design.md — "Riscos"), rebaseia os segmentos (tarefa 1.3) e os mapeia via `kernel::elf::load_segments` reaproveitado, localiza e faz o parsing da seção dinâmica (tarefas 2.2-2.7), carrega cada `DT_NEEDED` recursivamente em `/lib/<nome>` (empilhando `path` em `loading_stack` antes da recursão, desempilhando depois) antes de aplicar qualquer relocação própria, aplica cada relocação (tarefas 3.1-3.2, escrevendo diretamente no endereço final — ver design.md, "Relocações são escritas no endereço virtual final diretamente"), registra a nova `LoadedLibrary` em `ProcessDylibState.libraries` e devolve seu índice — sem teste de host possível para o mapeamento/escrita reais (mesma limitação de `kernel-elf-loader`); verificação real na tarefa 6.2
- [x] 4.3 Garantir que nenhuma falha em qualquer etapa de 4.2 deixa uma biblioteca parcialmente registrada em `ProcessDylibState.libraries` (só registrada após segmentos mapeados, dependências carregadas e todas as relocações aplicadas com sucesso) — verificar lendo o fluxo de controle (cada etapa usa `?` antes do `push` final)

- [x] 5.2 Implementar `sys_dlopen(ptr, len) -> u64`: lê o caminho via `core::slice::from_raw_parts`/`core::str::from_utf8` (mesmo padrão não validado de `sys_write`, UTF-8 inválido → `SYSCALL_ERROR`), monta `Fat32Filesystem` via `mount_boot_partition`, chama `load_library` (tarefa 4.2) com uma `loading_stack` nova e vazia, devolve o índice como `handle` ou `SYSCALL_ERROR`
- [x] 5.3 Implementar `sys_dlsym(handle, name_ptr, name_len) -> u64`: lê o nome do símbolo (mesmo padrão de 5.2), localiza `ProcessDylibState` do `root` corrente e a biblioteca em `handle` (fora de limites → `SYSCALL_ERROR`), varre `symbols` por nome igual, devolve o endereço encontrado ou `SYSCALL_ERROR`
- [x] 5.4 Registrar `SYSCALL_DLOPEN`/`SYSCALL_DLSYM` em `dispatch` (`kernel::syscall`) — verificar com `cargo kernel-build`
